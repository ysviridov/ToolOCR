# Stage 2.2 — ROI простых писем

## Область задачи

Stage 2.2 сфокусирован на простых внутренних письмах с рукописным или машинописным индексом и адресом получателя.

Заказные отправления в этот OCR-маршрут не входят. Их трек-номер/штрихкод должен считываться специализированным оборудованием; ToolOCR не тратит OCR на декодирование штрихкода.

Первый production-приоритет — формат `DL`, так как он составляет основную долю простых писем. Для текущей итерации ROI реализованы `DL`, `C5` и `C4`. C4 добавлен отдельно для визуальной валидации на реальном корпусе из 50 фотографий.

## Pipeline

```text
SOURCE
  -> frame normalization
  -> perspective rectification
  -> orientation 0/180
  -> canonicalization
       resolved 0   -> без поворота
       resolved 180 -> rotate 180
       ambiguous    -> не угадывать, ROI/OCR блокировать
  -> CANONICAL RECTIFIED
  -> ROI detection
       recipient_address
       recipient_postcode
  -> handwriting OCR (следующий этап)
  -> address parsing / validation
```

ROI всегда живут в системе координат `canonical_rectified`, где верх письма находится сверху независимо от исходного положения под камерой.

Orientation на этом этапе считается зафиксированной подсистемой. Настройка C4 ROI не должна менять orientation weights, thresholds или photometric preprocessing.

## Canonicalization

Модуль `ocr/app/roi.py` содержит `canonicalize_rectified()`.

Если orientation имеет статус `resolved` и значение `180`, rectified-изображение поворачивается на 180 градусов. При `ambiguous` изображение не поворачивается наугад, а `reliable=false`; ROI preview для такого кадра возвращает ошибку.

Это отдельный этап после perspective rectification. Frame normalization остаётся только геометрической подготовкой source-кадра и не меняет ориентацию письма.

## ROI текущей итерации

### `recipient_address`

Рукописный/машинописный адресный блок получателя. Визуально определяется внутри расширенной правой поисковой зоны, после чего OpenCV уточняет фактический bbox по компонентам текста/рукописи.

### `recipient_postcode`

Шестизначный индекс места назначения в специальном кодовом блоке простого письма. Декодирование цифр на этом этапе ещё не выполняется: задача Stage 2.2 — корректно локализовать область для последующего специализированного recognizer.

## Поисковые зоны и ГОСТ

Источником компоновки является ГОСТ Р 51506-99, обязательное приложение А (рисунки А.1/А.2 и таблица А.1). Таблица А.1 отдельно содержит размерную строку для C4 229×324 мм и размерные цепочки его адресных зон.

Текущие `GOST-guided search zones` намеренно шире нормативной разметки. Они являются зонами поиска ToolOCR, а не утверждением о точной нормативной границе адресной зоны. Это позволяет захватывать реальную рукопись, выходящую за направляющие линии.

Для C4 первая поисковая разметка в canonical normalized coordinates:

```text
recipient_address  x=0.49 y=0.30 w=0.48 h=0.48
recipient_postcode x=0.05 y=0.68 w=0.45 h=0.29
```

Эти значения считаются стартовыми и должны быть уточнены после визуальной проверки на 50 реальных C4-фотографиях. До этой проверки не следует сужать зоны только по одному или нескольким «красивым» образцам.

Дальше внутри зоны выполняется CV-refinement:

```text
GOST-guided search bbox
        +
foreground connected components
        -
длинные тонкие направляющие/рамки
        ->
detected bbox
```

В metadata сохраняются оба прямоугольника:

```json
{
  "kind": "recipient_address",
  "status": "detected",
  "confidence": 0.87,
  "search_bbox": {"x": 1000, "y": 320, "width": 900, "height": 500},
  "detected_bbox": {"x": 1080, "y": 370, "width": 730, "height": 350},
  "bbox": {"x": 1080, "y": 370, "width": 730, "height": 350},
  "component_count": 24,
  "ink_density": 0.018
}
```

Если содержимое уверенно не локализовано, статус региона становится `search_zone_only`; это не считается распознанным адресом.

## Debug overlay

В Test UI после layout-теста доступны две дополнительные кнопки:

- `Canonical` — rectified-письмо после обязательного поворота 0/180;
- `ROI` — canonical-письмо с разметкой ROI.

Цвета текущей итерации:

- зелёный — `recipient_address`;
- оранжевый — `recipient_postcode`.

Пунктирная рамка показывает расширенную поисковую зону. Толстая сплошная рамка показывает фактически найденный bbox. Рядом выводится тип ROI и confidence.

Preview генерируется по запросу и не сохраняется в Docker volume.

## Test UI API

```text
GET /v1/test-ui/images/{id}/canonical
GET /v1/test-ui/images/{id}/roi
GET /v1/test-ui/images/{id}/roi/meta
```

Query-параметры `format_mode` и `expected_format` совпадают с layout-анализом. UI автоматически использует режим и expected format соответствующего результата последнего теста.

`/roi/meta` возвращает структуру Stage 2.2 с canonical rotation и координатами двух ROI.

## Ограничения текущей итерации

- ROI поддерживаются для `DL`, `C5` и `C4`;
- распознавание цифр индекса ещё не выполняется;
- распознавание текста адреса ещё не выполняется;
- штрихкоды заказных отправлений не декодируются;
- при `orientation=ambiguous` ROI не строятся;
- C4 search zones пока являются расширенной стартовой разметкой и требуют corpus-validation;
- search zones пока не являются точной цифровой копией всех размерных цепочек приложения А.

После визуальной проверки C4 на полном 50-файловом наборе следует разделить ошибки на четыре класса: `ok`, `too_wide`, `too_narrow`, `wrong_content`. После этого можно корректировать только C4 search zones/CV-refinement, не затрагивая orientation.
