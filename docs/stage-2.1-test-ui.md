# Stage 2.1 — web-интерфейс тестирования

Для ручной проверки layout pipeline добавлен встроенный web-интерфейс:

```text
http://<host>:8090/test-ui
```

Он предназначен для разработки и приёмочных тестов Stage 2.1 и работает в том же контейнере `toolocr-ocr`.

## Возможности

- загрузка одного или нескольких изображений через drag&drop либо диалог выбора файлов;
- постоянное хранение исходных тестовых изображений в Docker named volume `toolocr_testdata`;
- выбор одного или нескольких ранее загруженных изображений;
- запуск полного `/v1/layout/analyze` для выбранного набора;
- краткая таблица результатов: файл, layout-статус, формат/ошибка, ориентация, normalization, total_ms;
- сводная статистика последнего прогона: количество файлов, успешные/ошибки, число определённых форматов и ориентаций, среднее/median/P95 времени;
- распределение результатов по форматам, ориентациям, layout-статусам и normalization-статусам;
- просмотр исходного изображения по кнопке `Исходное`;
- просмотр полного JSON результата по кнопке `Показать debug` с подсветкой синтаксиса JSON;
- просмотр normalized crop по кнопке `Normalized crop`;
- удаление выбранных исходных тестовых изображений из постоянного volume.

## Статистика последнего прогона

Статистика вычисляется в браузере из ответа `POST /v1/test-ui/run` и не требует отдельного backend endpoint.

В верхней части блока результатов отображаются:

```text
Всего
Успешно
Ошибки
Формат определён
Ориентация определена
Среднее, ms
Median, ms
P95, ms
```

Ниже выводятся распределения по:

```text
Форматы
Ориентация
Layout
Normalization
```

`P95` считается по `timing.total_ms` только для результатов, в которых время присутствует и является числом.

## Debug JSON

Кнопка `Показать debug` показывает полный JSON результата `analyze_layout()`.

Подсветка выполняется встроенным JavaScript без внешних CDN-зависимостей:

- ключи;
- строки;
- числа;
- boolean;
- `null`.

Перед вставкой значения экранируются, поэтому debug-данные не интерпретируются как HTML.

## Что сохраняется

Постоянно сохраняются только загруженные исходные изображения и небольшие JSON-sidecar файлы с их именем, размером и временем загрузки.

```text
/app/test-data
```

Каталог смонтирован как:

```yaml
- toolocr_testdata:/app/test-data
```

Поэтому пересборка и перезапуск контейнера `ocr` не удаляют библиотеку тестовых изображений.

## Что не сохраняется

`normalized crop` не записывается на диск. При нажатии кнопки UI повторно читает исходное изображение, выполняет `normalize_black_background()` в памяти и отдаёт JPEG с `Cache-Control: no-store`.

Результаты последнего запуска теста и рассчитанная статистика также не пишутся в volume: они хранятся только в состоянии открытой страницы браузера. После обновления страницы можно снова выбрать нужные исходные изображения и повторить тест.

## Запуск

После обновления ветки необходимо пересобрать OCR-контейнер, так как HTML входит в Docker image:

```bash
git pull
docker compose up -d --build ocr
```

Проверка:

```bash
make ocr-health
```

После этого открыть:

```text
http://<IP-сервера>:8090/test-ui
```

Если внешний порт изменён через `TOOLOCR_OCR_PORT`, использовать соответствующий порт.

## API тестового стенда

UI использует следующие endpoints:

```text
GET  /v1/test-ui/images
POST /v1/test-ui/images
POST /v1/test-ui/images/delete
POST /v1/test-ui/run
GET  /v1/test-ui/images/{id}/original
GET  /v1/test-ui/images/{id}/normalized
```

`POST /v1/test-ui/run` не реализует отдельный упрощённый алгоритм: backend вызывает тот же `analyze_layout()`, который используется endpoint `/v1/layout/analyze`. Поэтому консольные и web-тесты проходят через один pipeline.

## Ограничения

Тестовый UI пока не имеет аутентификации. Его следует публиковать только во внутренней сети разработки/сортировщика либо закрывать внешним reverse proxy.

По умолчанию один запуск ограничен 100 изображениями:

```text
TEST_UI_MAX_FILES_PER_RUN=100
```

Лимит одного загружаемого изображения совпадает с `OCR_MAX_UPLOAD_MB`, а ограничение числа пикселей — с `OCR_MAX_PIXELS`.
