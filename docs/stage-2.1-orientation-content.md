# Stage 2.1 — ориентация 0°/180° по содержимому письма

## Задача

Первоначальный orientation scoring использовал два асимметричных ГОСТ-якоря:

1. поле знаков почтовой оплаты справа сверху;
2. шестизначный кодовый штамп слева снизу.

На машинно оформленных отправлениях второй якорь часто отсутствует, а крупный штрихкод может ошибочно выглядеть как поле оплаты. Поэтому добавлен третий независимый канал `content_orientation`.

## Три канала

Для каждой гипотезы `0°` и `180°` теперь вычисляются:

```text
postage
code_stamp
content_orientation
```

`content_orientation` состоит из трёх подпризнаков:

```text
barcode_layout
address_layout
text_direction
```

### barcode_layout

Это не декодирование штрихкода. OpenCV ищет крупные области с сильным вертикальным градиентом и структурой линейного barcode.

В production-наблюдениях крупные машинные штрихкоды чаще расположены в левой части канонически ориентированного отправления. Поворот на 180° зеркально переносит такой блок вправо, что создаёт асимметричный сигнал.

Признак имеет ограниченный вес и не должен самостоятельно решать ориентацию.

### address_layout

Без OCR выделяются плотные горизонтальные текстоподобные компоненты. Каноническая гипотеза предпочитает:

```text
небольшой блок отправителя       -> верхняя левая часть
более крупный блок получателя    -> нижняя / правая часть
```

При повороте на 180° эта асимметрия меняется местами.

Признак не требует распознавания текста и работает также на части рукописных строк, если они образуют достаточно выраженные горизонтальные компоненты.

### text_direction

Для сложных случаев используется Tesseract OSD (`tesseract-ocr-osd`). OSD оценивает, требуется ли повернуть текст на `0°` или `180°`.

Если:

- текста слишком мало;
- OSD не уверен;
- OSD предлагает 90°/270°;
- компонент OSD недоступен;

то `text_direction=0` и этот канал не влияет на решение.

## Adaptive OSD

OSD существенно тяжелее OpenCV-признаков. Поэтому он запускается не всегда.

Сначала считаются:

```text
postage
code_stamp
barcode_layout
address_layout
```

Если visual-only решение уже имеет:

```text
best_score >= 0.38
margin     >= 0.18
```

OSD пропускается.

В остальных случаях OSD выполняется ровно один раз на rectified image.

OSD можно полностью отключить:

```text
ORIENTATION_TEXT_OSD=0
```

По умолчанию:

```text
ORIENTATION_TEXT_OSD=1
```

## Fusion

Внутри третьего канала сначала вычисляется CV-layout:

```text
cv_layout = 0.46 * barcode_layout + 0.54 * address_layout
```

Затем `content_orientation` выбирает наиболее сильное согласованное свидетельство между CV-layout и OSD.

Итоговый orientation score:

```text
anchor_agreement = sqrt(postage * code_stamp)

orientation_signal =
    0.24 * postage
  + 0.20 * code_stamp
  + 0.46 * content_orientation
  + 0.10 * anchor_agreement
```

Следствие: один ложный `postage=1` без других признаков даёт только `0.24` и не проходит стандартный порог `0.30`. Аналогично одиночный `code_stamp=1` даёт `0.20`.

Сильный `content_orientation` способен разрешить машинное отправление без шестизначного кодового штампа.

## Порог решения

Как и раньше:

```text
best_signal >= 0.30
margin      >= 0.12
```

Иначе ориентация остаётся:

```text
ambiguous
```

## Regression tests

Добавлены тесты:

- крупный barcode слева должен давать больший сигнал, чем после 180°;
- sender upper-left + recipient lower-right должны быть асимметричны;
- синтетический машинный DL без ГОСТ-кодового штампа должен разрешаться как 0°;
- его поворот должен разрешаться как 180°;
- одиночный ложный postage/code anchor не должен самостоятельно проходить orientation threshold.
