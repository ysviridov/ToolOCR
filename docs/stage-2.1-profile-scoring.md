# Stage 2.1 — ГОСТ profile scoring и ориентация 0°/180°

## Назначение

После поиска внешнего четырёхугольника и perspective rectification сервис проверяет две допустимые ориентации лицевой стороны письма: `0°` и `180°`.

Выбор выполняется средствами computer vision без запуска полного OCR. Это важно для производительности: распознавание текста не должно запускаться дважды только ради определения положения письма.

## Используемые признаки ГОСТ Р 51506-99

Scoring опирается на асимметричные элементы оформления лицевой стороны:

1. **Поле знака почтовой оплаты.** П. 6.1.2.5 задаёт поле 40×25 мм. На рисунках А.1/А.2 оно находится в верхней правой части около угловой метки.
2. **Шестизначный кодовый штамп.** Приложение Д, рисунок Д.1 задаёт шесть позиций с шагом 9 мм (`6×9=54`), верхние элементы 7×2 мм. Детектор ищет периодическую гребёнку в нижней левой части.
3. **Исполнение адресных зон.** П. 6.1.2.6 допускает сплошные и точечные линии. Большое число длинных горизонтальных элементов повышает вероятность исполнения I; отсутствие таких линий повышает вероятность исполнения II.
4. **Окно.** Для профилей приложения Б ищется структурный сигнал крупного прямоугольного окна в правой части лицевой стороны.
5. **Отношение сторон.** Используется как дополнительный признак формата. Для `partial_frame` его вес понижен, потому что обрезанный край искажает фактическое `L/H`.

Полный PDF стандарта в репозиторий не включается.

## Orientation signal

Ориентация не должна определяться одним только тёмным участком в зоне марки. На реальных письмах перевёрнутый кодовый штамп или штрихкод может оказаться в правом верхнем углу и дать высокий ложный `postage`.

Поэтому `orientation_signal` теперь учитывает согласованность двух асимметричных ГОСТ-якорей одновременно:

```text
верх справа  -> поле марки / знака оплаты
низ слева    -> шестизначный кодовый штамп
```

Используется взвешенная комбинация `postage`, `code_stamp` и их геометрического среднего. Последний член повышает score, когда оба ожидаемых якоря присутствуют одновременно.

## Partial frame

`frame_contact_sides` используется для оценки достоверности внешней геометрии и метрического размера, но **не уменьшает уже реально обнаруженный visual-якорь**.

Это принципиально: контакт физической границы письма с краем фотографии ещё не означает, что поле марки или кодовый штамп не видны. Старое поведение умножало `postage`/`code_stamp` на фиксированный штраф и на реальном перевёрнутом C5 приводило к ошибочному выбору `0°`.

Теперь:

- `aspect` при `partial_frame` имеет меньший вес;
- метрический слой помечает соответствующую размерность как `lower_bound`;
- `postage` и `code_stamp` оцениваются по фактически присутствующему изображению без искусственного штрафа;
- если якорь действительно обрезан, его score естественным образом уменьшается из-за отсутствующих элементов;
- ориентация остаётся `ambiguous`, если отрыв двух гипотез недостаточен.

## Производительность

Перед scoring rectified image уменьшается до 1000 px по длинной стороне. Все геометрические признаки заданы в миллиметрах, поэтому такое уменьшение не меняет физическую модель.

Тяжёлые признаки считаются один раз на физический формат (`C6`, `DL`, `C5`, `C4`, `B4`) и повторно используются для вариантов исполнения I/II и с окном/без окна.

При наличии camera-plane calibration физический формат определяется метрически первым, и visual scoring выполняется только внутри уже найденного формата.

## Ответ API

`POST /v1/layout/analyze` содержит:

```json
{
  "orientation": {
    "status": "resolved",
    "value_deg": 180,
    "confidence": 0.78,
    "margin": 0.35,
    "scores": [
      {"orientation_deg": 0, "score": 0.42},
      {"orientation_deg": 180, "score": 0.78}
    ]
  },
  "profile_scoring": {
    "status": "resolved",
    "profile_id": "vn-c5-i",
    "selected": {
      "format": "C5",
      "layout": "I",
      "window": false
    }
  }
}
```

Числа являются иллюстративными и зависят от фотографии.

Каждая запись `top_hypotheses` содержит компоненты:

```json
{
  "components": {
    "aspect": 0.78,
    "postage": 0.97,
    "code_stamp": 0.57,
    "layout": 1.0,
    "window": 1.0,
    "orientation_signal": 0.78
  }
}
```

## Консервативное решение

Ориентация считается определённой, только если:

- лучший `orientation_signal >= 0.30`;
- отрыв от второй ориентации `margin >= 0.12`.

Иначе:

```json
{
  "orientation": {
    "status": "ambiguous",
    "value_deg": null
  }
}
```

## Проверка

После обновления ветки:

```bash
cd /opt/ToolOCR
git fetch origin
git switch stage-2.1-layout
git pull

docker compose up -d --build ocr
```

Проверка JSON:

```bash
make layout-smoke FILE=/path/letter.jpg \
  | jq '{
      layout_status,
      metric_format,
      orientation,
      format_status,
      profile_scoring,
      timing
    }'
```

Canonical rectification:

```bash
OUT=/tmp/canonical.jpg make layout-rectify FILE=/path/letter.jpg
```

Диагностический rectification без исправления `0°/180°`:

```bash
OUT=/tmp/raw.jpg make layout-rectify-raw FILE=/path/letter.jpg
```

Если orientation `ambiguous`, canonical endpoint не угадывает направление и оставляет изображение без поворота.
