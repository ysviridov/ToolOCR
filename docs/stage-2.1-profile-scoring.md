# Stage 2.1 — ГОСТ profile scoring и ориентация 0°/180°

## Назначение

После поиска внешнего четырёхугольника и perspective rectification сервис проверяет две допустимые ориентации лицевой стороны письма: `0°` и `180°`.

Выбор выполняется комбинацией быстрых computer-vision признаков и, только для спорных случаев, Tesseract OSD. Полный OCR адреса на этом этапе не запускается.

## Используемые признаки

Scoring использует несколько независимых асимметричных каналов:

1. **Поле знака почтовой оплаты (`postage`).** П. 6.1.2.5 задаёт поле 40×25 мм в верхней правой части.
2. **Шестизначный кодовый штамп (`code_stamp`).** Приложение Д, рисунок Д.1: шесть позиций с шагом 9 мм; детектор ищет характерную периодическую структуру в нижней левой части.
3. **Крупный линейный штрихкод (`barcode_layout`).** Определяется без декодирования по вертикальному градиенту и асимметрии положения.
4. **Адресные блоки (`address_layout`).** Плотные горизонтальные строки группируются морфологией; каноническая гипотеза предпочитает меньший блок отправителя сверху слева и более крупный блок получателя ниже/правее.
5. **Направление текста (`text_direction`).** Для спорных случаев запускается Tesseract OSD. Он получает отдельное изображение до `ORIENTATION_TEXT_OSD_MAX_SIDE=1800` px по длинной стороне.
6. **Исполнение адресных зон (`layout`)**, окно и отношение сторон используются для выбора конкретного ГОСТ-профиля, но не являются самостоятельными основными каналами ориентации.

Полный PDF стандарта в репозиторий не включается.

## Базовый orientation score

Сначала для каждой гипотезы строится `content_orientation` из `barcode_layout`, `address_layout` и `text_direction`, затем считается базовый score:

```text
anchor_agreement = sqrt(postage * code_stamp)

base_score =
    0.24 * postage
  + 0.20 * code_stamp
  + 0.46 * content_orientation
  + 0.10 * anchor_agreement
```

Один ложный `postage=1.0` без других подтверждений даёт только `0.24` и сам по себе не проходит минимальный порог ориентации `0.30`.

## Contrast-aware fusion

Высокое абсолютное значение признака не всегда означает, что он полезен для `0°/180°`. Например:

```text
barcode[0]   = 0.7195
barcode[180] = 0.7070
```

Оба значения велики, но разница почти нулевая. Такой barcode практически не содержит информации о направлении.

Поэтому после базового score для каждого канала вычисляется только положительный направленный контраст:

```text
delta[channel, 0]   = max(0, channel[0]   - channel[180])
delta[channel, 180] = max(0, channel[180] - channel[0])
```

Каналы имеют веса:

```text
postage        0.18
code_stamp     0.20
barcode_layout 0.20
address_layout 0.12
text_direction 0.30
```

`contrast_bonus` равен `0.20 * weighted_delta` и ограничен сверху значением `0.08`.

Таким образом, почти симметричный barcode получает почти нулевой bonus, а реальная асимметрия между гипотезами увеличивает margin.

## Agreement bonus

Если несколько независимых каналов одновременно голосуют в одну сторону, это более сильное свидетельство, чем один канал.

Канал считается поддерживающим гипотезу, если его направленный `delta >= 0.06`. Если таких каналов минимум два, начисляется:

```text
agreement_bonus = 0.25 * sqrt(top_delta_1 * top_delta_2)
```

с ограничением сверху `0.10`.

Итог:

```text
orientation_score =
    base_score
  + contrast_bonus
  + agreement_bonus
```

Все три части ограничиваются так, чтобы новый слой увеличивал разрыв между согласованными гипотезами, но не заменял исходные ГОСТ/content-сигналы.

## Порог решения

Пороги после введения contrast-aware fusion **не снижались**:

```text
best_score >= 0.30
margin     >= 0.12
```

Если хотя бы одно условие не выполнено, результат остаётся `ambiguous`.

## Debug JSON

`orientation.evidence` показывает абсолютные сигналы, базовый score, направленные delta и оба bonus:

```json
{
  "orientation_deg": 0,
  "postage": 0.9894,
  "code_stamp": 0.0,
  "barcode_layout": 0.7195,
  "address_layout": 0.3351,
  "text_direction": 0.4493,
  "content_orientation": 0.5119,
  "base_score": 0.4729,
  "contrast": {
    "postage_delta": 0.2662,

    "barcode_delta": 0.0125,
```

Числа являются примером диагностического расчёта и зависят от конкретной фотографии.

## Partial frame

`frame_contact_sides` используется для оценки достоверности внешней геометрии и метрического размера, но не уменьшает уже реально обнаруженный visual-якорь.

Контакт физической границы письма с краем фотографии ещё не означает, что поле марки, кодовый штамп или контент внутри письма не видны. Если элемент действительно обрезан, его score естественным образом уменьшается из-за отсутствующих данных.

## Производительность: CV-first / OSD fallback

Быстрый CV-scoring выполняется на копии до 1000 px по длинной стороне. После вычисления `postage`, `code_stamp`, `barcode_layout` и `address_layout` сразу выполняется **полный contrast-aware fusion без `text_direction`**.

Если уже на этом этапе выполняются обычные production-пороги:

```text
best_score >= 0.30
margin     >= 0.12
```

ориентация считается достаточно надёжной для fast path, и Tesseract OSD вообще не запускается.

Только если CV-only fusion остаётся неоднозначным, запускается slow path:

```text
CV признаки
    ↓
contrast-aware fusion без OSD
    ↓
resolved? ── yes ──> готово
    │
    no
    ↓
Tesseract OSD до 1800 px
    ↓
повторный base score + contrast/agreement fusion
    ↓
финальное решение
```

Таким образом, дорогой процесс Tesseract используется как fallback, а не как обязательная часть большинства писем. Пороги fast path и финального решения одинаковы; ускорение не достигается ослаблением требований к уверенности.

При наличии camera-plane calibration физический формат определяется метрически первым, и visual scoring выполняется только внутри уже найденного формата.

## Проверка

После обновления ветки:

```bash
cd /opt/ToolOCR
git pull
docker compose up -d --build ocr
```

Для массовой проверки предпочтителен встроенный test UI. После прогона можно выгрузить единый debug JSON и сравнить `orientation.evidence` и `timing.profile_scoring_ms` для всех файлов.

Консольный вариант:

```bash
make layout-smoke FILE=/path/letter.jpg \
  | jq '{orientation, format_status, profile_scoring, timing}'
```

Canonical rectification:

```bash
OUT=/tmp/canonical.jpg make layout-rectify FILE=/path/letter.jpg
```

Если orientation `ambiguous`, canonical endpoint не угадывает направление и оставляет изображение без поворота.
