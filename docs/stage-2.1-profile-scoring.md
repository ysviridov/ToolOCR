# Stage 2.1 — ГОСТ profile scoring и ориентация 0°/180°

## Назначение

После поиска внешнего четырёхугольника и perspective rectification сервис проверяет две допустимые ориентации лицевой стороны письма: `0°` и `180°`.

Выбор выполняется средствами computer vision без запуска полного OCR. Это важно для производительности: распознавание текста не должно запускаться дважды только ради определения положения письма.

## Используемые признаки ГОСТ Р 51506-99

Scoring опирается на асимметричные элементы оформления лицевой стороны:

1. **Поле знака почтовой оплаты.** П. 6.1.2.5 задаёт поле 40×25 мм. На рисунках А.1/А.2 оно находится в верхней правой части около угловой метки. Сильная печать/марки в этой области являются главным сигналом ориентации.
2. **Шестизначный кодовый штамп.** Приложение Д, рисунок Д.1 задаёт шесть позиций с шагом 9 мм (`6×9=54`), верхние элементы 7×2 мм и размерную линию `25±2,5` мм. Детектор ищет периодическую гребёнку в нижней левой части.
3. **Исполнение адресных зон.** П. 6.1.2.6 допускает сплошные и точечные линии. Большое число длинных горизонтальных элементов повышает вероятность исполнения I; отсутствие таких линий повышает вероятность исполнения II.
4. **Окно.** Для профилей приложения Б ищется структурный сигнал крупного прямоугольного окна в правой части лицевой стороны.
5. **Отношение сторон.** Используется как дополнительный признак формата. Для `partial_frame` его вес понижен, потому что обрезанный край искажает фактическое `L/H`.

Полный PDF стандарта в репозиторий не включается.

## Производительность

Перед scoring rectified image уменьшается до 1000 px по длинной стороне. Все геометрические признаки заданы в миллиметрах, поэтому такое уменьшение не меняет физическую модель.

Тяжёлые признаки считаются один раз на физический формат (`C6`, `DL`, `C5`, `C4`, `B4`) и повторно используются для вариантов:

- исполнение I / II;
- с окном / без окна.

На тестовом CPU это сокращает profile scoring с нескольких секунд примерно до сотен миллисекунд.

## Компоненты score

Каждая запись `top_hypotheses` содержит:

```json
{
  "profile_id": "vn-c4-i",
  "orientation_deg": 0,
  "score": 0.81,
  "components": {
    "aspect": 0.74,
    "postage": 0.93,
    "code_stamp": 0.48,
    "layout": 1.0,
    "window": 1.0,
    "orientation_signal": 0.74
  }
}
```

Интерпретация:

- `aspect` — согласованность отношения сторон с форматом;
- `postage` — сигнал поля марки/знака оплаты;
- `code_stamp` — соответствие шестизначному кодовому штампу;
- `layout` — соответствие исполнению I или II;
- `window` — соответствие профилю с окном/без окна;
- `orientation_signal` — асимметричный сигнал, используемый именно для выбора `0°/180°`.

## Консервативное решение

Ориентация считается определённой, только если:

- лучший `orientation_signal >= 0.30`;
- отрыв от второй ориентации `margin >= 0.12`.

Иначе:

```json
{
  "orientation": {
    "status": "ambiguous",
    "value_deg": null
  }
}
```

Профиль тоже не выбирается принудительно. Требуется достаточный общий score и отрыв от следующей гипотезы. Это особенно важно для близких форматов C6/C5/C4/B4.

## Partial frame

При касании письмом края исходного кадра:

- `aspect` получает меньший вес;
- якорь, находящийся на обрезанной стороне, получает меньший вес;
- список сторон `frame_contact_sides` преобразуется отдельно для гипотез `0°` и `180°`;
- профиль может быть определён по внутренним физическим якорям даже при ненадёжном `L/H`.

Если profile scoring уверенно определил профиль на частичном кадре, `format_status` становится:

```text
resolved_by_profile_scoring_partial_frame
```

Если уверенности недостаточно:

```text
unreliable_partial_frame
```

## Проверка на реальной фотографии

После обновления ветки:

```bash
cd /opt/ToolOCR
git fetch origin
git switch stage-2.1-layout
git pull

docker compose up -d --build ocr
```

Проверка JSON:

```bash
make layout-smoke FILE=/path/letter.jpg \
  | jq '{
      layout_status,
      detector,
      orientation,
      format_status,
      profile_scoring,
      timing
    }'
```

Для первых тестов особенно полезно смотреть top-4:

```bash
make layout-smoke FILE=/path/letter.jpg \
  | jq '{
      orientation,
      profile: .profile_scoring | {
        status,
        profile_id,
        confidence,
        margin,
        top_hypotheses: .top_hypotheses[0:4]
      },
      timing
    }'
```

## Canonical rectification

`make layout-rectify` теперь по умолчанию применяет найденную ориентацию. Если письмо было снято вверх ногами и scoring уверенно выбрал `180°`, выходной JPEG будет автоматически повёрнут:

```bash
OUT=/tmp/canonical.jpg make layout-rectify FILE=/path/letter.jpg
```

Для сравнения с исходным rectification без исправления `0°/180°`:

```bash
OUT=/tmp/raw.jpg make layout-rectify-raw FILE=/path/letter.jpg
```

Если orientation `ambiguous`, canonical endpoint не угадывает направление и оставляет изображение без поворота.

## Что собрать для настройки порогов

Для проблемного письма достаточно сохранить:

1. исходный JPEG;
2. вывод `orientation`;
3. первые 4–8 `top_hypotheses` вместе с `components`;
4. `timing.profile_scoring_ms`;
5. canonical и raw rectified JPEG, если ориентация выбрана неверно.

По этим данным можно настраивать веса и пороги отдельно от OCR.
