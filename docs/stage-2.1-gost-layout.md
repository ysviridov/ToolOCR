# Stage 2.1 — сегментация конверта по ГОСТ Р 51506-99

## Production-вход

В продуктивном режиме ToolOCR принимает **только полную фотографию лицевой стороны почтового отправления**. Предварительно вырезанные адресные кропы, отдельные поля формы и ручные ROI в production pipeline не используются.

Сортировщик может подать письмо под камеру в двух допустимых ориентациях:

- штатная ориентация `0°`;
- письмо развёрнуто на `180°` и сфотографировано вверх ногами.

Поэтому после обнаружения границ конверта и perspective rectification изображение ещё не считается канонически ориентированным. До применения координат ГОСТ алгоритм обязан проверить обе гипотезы `0°` и `180°`.

## Источник геометрии

Для сегментации лицевой стороны почтового конверта используется ГОСТ Р 51506-99 «Конверты почтовые. Технические требования. Методы контроля».

В коде стандарт рассматривается как источник геометрии и вариантов оформления, а не как обучающий датасет. Полный текст ГОСТ в публичный репозиторий не включается.

Основные ссылки на стандарт:

- п. 4.1.1, таблица 1 — стандартные размеры C6, DL, C5, C4, B4;
- п. 4.1.4 — исполнения адресных зон I (направляющие линии) и II (угловые элементы);
- п. 4.1.5.1 — оформление внутренних почтовых отправлений;
- п. 6.1.2.5 — поле 40×25 мм под марку/иной знак почтовой оплаты;
- п. 6.1.2.6 — требования к линиям адресных зон;
- обязательное приложение А, рисунки А.1/А.2 и таблица А.1 — лицевая сторона внутренних конвертов без окна;
- обязательное приложение Б, рисунки Б.1/Б.2 и таблица Б.1 — внутренние конверты с окном;
- обязательное приложение Д — кодовые штампы.

## Важное следствие

Формат конверта нельзя надёжно определить только по отношению сторон фотографии.

DL имеет отношение сторон около 2:1, но C6, C5, C4 и B4 имеют очень близкие отношения сторон. Поэтому алгоритм обязан возвращать несколько кандидатов и выбирать формат по совокупности стандартных признаков после перспективного выравнивания.

Поворот на 180° не меняет отношение сторон, поэтому предварительный список кандидатов формата можно строить до определения ориентации.

## Система координат

После обнаружения четырёх углов лицевой стороны выполняется perspective rectification. Затем выбирается каноническая ориентация `0°` или `180°`.

Только после выбора ориентации изображение переводится в систему координат ГОСТ:

- начало — левый верхний угол **канонически ориентированной** лицевой стороны;
- X — вправо;
- Y — вниз;
- размеры — в миллиметрах выбранного формата.

После определения формата любой ROI задаётся в миллиметрах и только на последнем шаге переводится в пиксели.

Это позволяет не хранить отдельные «магические» pixel coordinates для разных разрешений камеры.

## Определение ориентации 0/180

Для каждого rectified-изображения строятся две гипотезы:

```text
H0   = изображение как после rectification
H180 = ROTATE_180(H0)
```

Обе гипотезы оцениваются тем же ГОСТ-profile matcher. Основные якоря:

- ожидаемая зона марки/знака оплаты;
- кодовый штамп;
- адресная зона отправителя;
- адресная зона адресата;
- направляющие линии либо угловые элементы;
- окно, если оно предусмотрено профилем.

Принципиально важно: ориентация определяется **до OCR адреса**. Полнотекстовый OCR не должен запускаться дважды только для того, чтобы понять, где верх конверта.

Пример результата layout matcher:

```json
{
  "standard": "ГОСТ Р 51506-99",
  "format": "C6",
  "layout": "I",
  "window": false,
  "orientation_deg": 180,
  "confidence": 0.94,
  "orientation_confidence": 0.98
}
```

Если scores гипотез `0°` и `180°` близки, система не должна угадывать. Возвращается `orientation_status=ambiguous`, и OCR адресных ROI не запускается до разрешения неоднозначности следующей ступенью pipeline.

## Pipeline Stage 2.1

```text
полная фотография письма
   │
   ▼
поиск внешнего четырёхугольника конверта
   │
   ▼
perspective rectification
   │
   ▼
кандидаты формата по H/L
   │
   ▼
две гипотезы ориентации
   ├─ 0°
   └─ 180°
   │
   ▼
ГОСТ profile scoring для каждой гипотезы
   ├─ поле марки 40×25 мм
   ├─ кодовый штамп
   ├─ направляющие линии / угловые элементы
   └─ окно, если оно присутствует
   │
   ▼
format + layout + orientation + confidence
   │
   ▼
каноническая миллиметровая система координат
   │
   ├─ recipient_address ROI
   ├─ recipient_postcode ROI
   ├─ sender_address ROI
   ├─ sender_postcode ROI
   └─ служебные/исключаемые зоны
   │
   ▼
OCR только необходимых ROI
```

## Почему нельзя сначала запустить OCR для определения ориентации

Главная цель Stage 2.1 — сократить стоимость распознавания и стабилизировать геометрию. Если выполнять полный OCR для обеих ориентаций, мы фактически удваиваем самый дорогой этап pipeline.

ГОСТ уже задаёт асимметричное расположение стандартных элементов, поэтому ориентацию можно оценивать средствами computer vision и template scoring. OCR остаётся дополнительным слабым сигналом только для неоднозначных случаев, а не основным способом выбора `0°/180°`.

## Поддерживаемые профили

Первый инкремент Stage 2.1 должен поддерживать внутренние отправления:

1. без окна, исполнение I — рисунок А.1;
2. без окна, исполнение II — рисунок А.2;
3. затем с окном — приложение Б.

Международные и авиационные варианты добавляются после стабилизации внутреннего профиля.

## Определение формата

Этап 1 — отношение сторон. Оно используется только как предварительный фильтр.

Этап 2 — template scoring. Для каждого кандидата и для каждой ориентации строится проекция стандартных элементов в нормализованную фотографию и оценивается совпадение:

- края/линии;
- положение поля марки;
- кодовый штамп;
- направляющие линии адресной зоны;
- окно.

Если два профиля имеют близкий score, сервис не должен «угадывать»: возвращается список кандидатов или `layout_status=ambiguous`.

## Требования к реализации

- production input — только полная фотография письма;
- обязательно поддерживаются ориентации `0°` и `180°`;
- никаких приблизительных координат зон «на глаз»;
- числовые размеры ROI должны иметь ссылку на конкретный рисунок/таблицу ГОСТ в комментарии к профилю;
- размеры хранятся в мм, а не пикселях;
- перспектива исправляется до определения ориентации и сегментации;
- ориентация определяется до запуска OCR адресных ROI;
- формат, вариант оформления и ориентация сопровождаются confidence;
- при недостаточном confidence возвращается `unknown/ambiguous`, а не произвольный профиль;
- фотографии, на которых полный контур письма надёжно не найден, должны завершаться layout reject, а не переходить к crop fallback.
